# 共通コーディングルール

AIエージェント（Claude Code / Antigravity など）が、この環境で開発作業をするときに必ず守るルール。
**どのアプリにも共通する内容だけ**をここに書く。個別アプリの事情は、各プロジェクト直下の `AGENTS.md` に書く。

---

## 1. 想定している技術構成

特に指定がなければ、アプリは次の構成で作る。

| 層 | 使うもの |
| --- | --- |
| 画面 | HTML 1ファイル（CSS・JavaScript も同じファイルに同梱） |
| サーバー処理 | Google Apps Script（`.gs`、言語はJavaScript／V8ランタイム） |
| データの保存先 | Googleスプレッドシート |
| 画面とサーバーの橋渡し | `google.script.run` |
| 公開 | Apps Script のウェブアプリ（`/exec` で終わるURL） |

この構成を選ぶ理由は、サーバーの契約もデータベースの構築も不要で、Googleアカウントの認証をそのまま使えるため。

> **新規アプリは `NEW_APP.md` の構成を標準とする。** 画面は GitHub Pages、GAS は `fetch` で呼ぶAPI、デプロイは GitHub Actions。
> この構成では `google.script.run` は使わず、`/exec` のURLは `config.js` にだけ書いてよい（§6 の例外）。

### 構成上の注意

- `index.html` は画面のみ。**スプレッドシートを直接は読めない**。必ず `google.script.run` 経由でサーバー側の関数を呼ぶ
- `doGet()` で HTML を返すときのファイル名は、**拡張子を除いた名前**で指定する（`index.html` なら `'index'`）
- `<base target="_top">` を `<head>` に必ず入れる（ウェブアプリはiframeの中で動くため）
- サーバー側のファイルは `.gs` か `.js` のどちらかに統一する。**混在させない**（アップロード時に重複ファイルが生まれる）

## 2. 開発の基本フロー

**ローカルのファイルが正。** 手順は必ずこの順番で行う。

1. ローカルのファイルを編集する
2. アップロードする（`clasp push`）
3. 公開を更新する（`clasp deploy`）
4. ブラウザで強制リロードして確認する（`Ctrl + F5`）

### 絶対にやってはいけないこと

- **ブラウザのApps Scriptエディタで直接コードを編集しない。** `clasp push` はサーバー側を丸ごと上書きするため、編集内容が消える
  - もし触ってしまった場合は、次のpushの前に必ず `clasp pull` で取り込む
- **同じファイルを2箇所に置かない。** プロジェクトフォルダ直下の1箇所だけで管理する

---

## 3. clasp（デプロイ用ツール）

`clasp` は、ローカルのファイルとApps Scriptプロジェクトをやりとりするコマンドラインツール。

### コマンド対応表

| やりたいこと | コマンド |
| --- | --- |
| ローカル → サーバーに反映 | `clasp push -f` |
| サーバー → ローカルに取り込み | `clasp pull` |
| 同じURLのまま公開を更新 | `clasp deploy -i <デプロイID> -d "<変更メモ>"` |
| URL・デプロイ一覧を見る | `clasp deployments` |
| ブラウザでエディタを開く | `clasp open` |
| アップロード対象ファイルの確認 | `clasp status` |
| 新規プロジェクトを作る（シート連動） | `clasp create --type sheets --title "<名前>"` |
| 新規プロジェクトを作る（単独ウェブアプリ） | `clasp create --type webapp --title "<名前>"` |

### 最重要：push と deploy は別物

- `push` は「コードをサーバーに置いた」だけ。**これだけではURLの中身は変わらない**
- `/exec` のURLは、**デプロイした時点のバージョンを固定で配信し続ける**
- 「直したのに変わらない」ときは、①`deploy` をしていない ②`Ctrl + F5` ではなく通常のリロードでキャッシュが効いている、の順に疑う

### deploy は必ず `-i` を付ける

`-i <デプロイID>` を付けないと**新しいURLが増えてしまう**。既存アプリの更新では必ず既存のデプロイIDを指定する。

### 新規プロジェクトの初回だけはブラウザが必要

承認ダイアログ（「このアプリは確認されていません」→ 詳細 → 移動 → 許可）は、ブラウザでしか出せない。
初回は `clasp open` でエディタを開き、「デプロイ」→「新しいデプロイ」→ 種類「ウェブアプリ」から公開する。
発行されたURLの `/s/` と `/exec` に挟まれた部分がデプロイID。**これをプロジェクト内のメモファイルに控える**。

## 4. ターミナルの書き方（この環境固有）

**このPCのターミナルは Windows PowerShell 5.1。**

- **`&&` は使えない。** `トークン '&&' は、このバージョンでは有効なステートメント区切りではありません` というエラーになる
  - 連結は `;` と `if ($?) { ... }` で書く
- **必ず先頭に `cd "<プロジェクトフォルダの絶対パス>"` を付ける。** ターミナルはホームフォルダで開くため、そのままでは `clasp` が `.clasp.json` を見つけられない
- ユーザーに渡すコードブロックは **bashタグ**で書く（実行ボタンが付くのがbashタグだけのため）。タグは表示上のラベルにすぎず、実際に動くのはPowerShell

定型：

```
cd "<プロジェクトフォルダ>"; clasp push -f; if ($?) { clasp deploy -i <デプロイID> -d "<変更メモ>" }
```

## 5. git のルール

- **作業を始める前に、必ず現状をコミットしておく。** 変更が壊れたときに戻れる状態を作ってから手を入れる
- 1つの機能・1つの修正につき1コミット。無関係な変更を混ぜない
- コミットメッセージは日本語でよい。「何を変えたか」が一行でわかるように書く
- `git commit -am` で雑にまとめず、`git status` で対象を確認してからコミットする
- **破壊的な操作（`reset --hard`、`push --force`、`checkout --` など）は、実行前に必ずユーザーに確認する**
- ブランチを切る必要がある規模かどうか迷ったら、ユーザーに聞く

## 6. 秘密情報の扱い

**次のものは、ドキュメント・コミット・チャットへの貼り付けのいずれにも書かない。**

- APIキー、アクセストークン、パスワード
- スクリプトID、デプロイID、スプレッドシートID
- ウェブアプリの `/exec` URL（デプロイIDが含まれるため。GitHub Pages 構成の `config.js` だけは例外。`NEW_APP.md` 参照）
- 個人情報（氏名・メールアドレス・電話番号などの実データ）

### 運用方法

- IDやURLは、プロジェクト内のメモファイル（例：`アプリURL.txt`）にまとめ、**`.gitignore` に入れる**
- `.clasp.json` はスクリプトIDを含むので `.gitignore` に入れる。消えても、Apps Scriptエディタの「プロジェクトの設定」からスクリプトIDを取り直して作り直せる
- ドキュメントに書くときは `<デプロイID>` のようなプレースホルダにして、「実際の値は○○に書いてある」と場所だけ示す
- **`~/.clasprc.json` は認証情報そのもの。** 絶対に開かない・コピーしない・中身を表示しない
- スプレッドシートの実データ（人名や金額）を、確認のために読む必要がないなら読まない

## 7. コードの書き方

- **既存ファイルの全面書き直しはしない。** 該当箇所だけを差分で直す
- 周りのコードのスタイル（命名・コメントの量・書き方の癖）に合わせる。自分の好みで統一し直さない
- **スプレッドシートの列構成と既存データを壊さない。** 列の追加・並べ替え・削除や、既存行の一括書き換えは、実行前にユーザーに確認する
- 頼まれていない機能追加や設計変更をしない。「今は動かすこと」が目的のときは、最小の変更で終える
- 修正したら、**何をなぜ変えたかを1〜2行で説明する**

### 動作確認

- ブラウザを使わずに確認できることは、先に確認する（構文チェックなど）
- HTMLに埋め込んだJavaScriptは、`<script>` の中身を取り出して `node --check` にかければ構文エラーを見つけられる
- 「直したつもり」で報告しない。確認できていないことは「未確認」と明記する

---

## 8. 説明の仕方

**ユーザーはプログラミング初心者。**

- 日本語で説明する。専門用語には短い補足を添える（例：「`push`（コードをサーバーに置くこと）」）
- 手順は「上から順にやれば終わる」形で番号を振る
- 原因が特定できていない段階では、**切り分けの手順**を先に示す。推測で修正を重ねない
- エラーが出たら、ユーザーに何を見てほしいのか（どの画面のどの行か）を具体的に指示する
- 選択肢を並べるだけで終わらせない。推奨案を先に出す
